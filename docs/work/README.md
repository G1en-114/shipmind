# 后续工作入口

本目录是接手后的执行骨架。依据 [审查与计划](../TAKEOVER-REVIEW-PLAN.md)，覆盖阶段 1–6；业务修复、真机验证和发布均未启动。旧 HANDOFF、MASTER-CHECKLIST 的历史状态不能替代这里的验收记录。

## 文件职责

| 文件 | 用途 |
|---|---|
| [tasks.json](tasks.json) | 唯一任务状态表：14 项工作的优先级、依赖、涉及文件和验收 ID |
| [acceptance.json](acceptance.json) | 18 项验收规格；当前全部 not_run，不是可运行测试集 |
| [artifacts.json](artifacts.json) | 夹具、声纹模型、合成手册的制品清单骨架；来源/校验待补 |
| [执行记录模板](templates/execution-record.json) | 每项任务完成后记录版本、环境、变更、验证与局限 |
| [提交物料工作表](DELIVERY.md) | 视频、征文、合影、规则与最终提交的交付槽位 |
| [workboard.py](../../scripts/workboard.py) | 只读检查任务引用、依赖环、状态与证据是否缺失 |

## 从这里开工

在仓库根目录使用 PowerShell 单行命令：

```powershell
python scripts/workboard.py check
```

```powershell
python scripts/workboard.py status
```

```powershell
python scripts/workboard.py next
```

首批就绪任务为 R01、R02、R05。检查命令不会执行命令清单、连接网络、部署或运行产品测试。检查通过只说明任务骨架一致，不能证明产品可用。

## 实施约定

1. 从 next 选择一项，阅读审查对应条目与关联验收规格，将任务改为 in_progress。按涉及文件落地最小修复，不新建空业务模块。
2. 将验收规格转换成实际测试或人工验证步骤。离线、Web、GB10、在线、人工各自记录，跳过不得计为通过。优先建立 R08 的评测分组，其他任务的针对性测试不必等待全部测试框架完工。
3. 使用模板保存 `docs/work/records/<任务ID>.json`；真实日志、截图和大制品保存到 `runs/work/<任务ID>/`，记录相对路径与必要散列。records 目录在首次有真实记录时创建，不预填成功记录。跨机器验收需要可获取的归档位置，不能只引用本地忽略目录。
4. 记录 check 项时包含 acceptance_id、实际命令/操作、退出码、结果、证据路径。更新 acceptance.json 的状态与证据；只有必需验收通过、依赖完成且存在记录，任务才能标 done。
5. 改动范围扩大时更新任务及验收规格，再运行 check。blocked 必须在 notes 说明真实依赖；P2 新想法放入计划的延期区，不混入当前关键路径。

## 阶段交接门槛

- 阶段 1：可复现依赖/夹具/制品、自检和部署包内容就绪。
- 阶段 2：失败处理、路由、报告审核与机舱闭环成立。
- 阶段 3：内容级评测、Web 场景切换及指标边界成立。
- 阶段 4：官方 GB10 同版本验收、在线增强单列、文档口径一致。
- 阶段 5：视频、征文、团队材料形成可审阅成品。
- 阶段 6：核实规则、检查链接，按后续发布授权提交并存回执。

日期沿用旧计划，仅作安排假设。V01 的真机验收尚未执行；D01 的脚本和素材整理可提前准备，最终完成依赖冻结能力及真机证据。D02 的规则核实也应提前开始，发布/提交在材料就绪后执行。
